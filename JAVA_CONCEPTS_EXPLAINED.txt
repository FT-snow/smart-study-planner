================================================================================
SMART STUDY PLANNER - JAVA CONCEPTS USED IN THE BACKEND, EXPLAINED SIMPLY
================================================================================

This file explains every Java (OOP) concept the Spring Boot backend uses, in
plain words. Only concepts covered in the CSC2104 lectures (and a handful of
fixed Spring annotations) appear here.

THE WHOLE BACKEND IS 12 FILES, ALL IN ONE FOLDER (backend/src/main/java/
studyplanner/), ALL IN ONE PACKAGE - so classes see each other directly,
without import mountains:

  StudyPlannerApplication.java  -> the start button
  PlannerController.java        -> every web address, in sections
  ApiErrors.java                -> the one central try/catch for the app
  ProgressCalculator.java       -> dashboard math (the Lecture 14 class)
  SamplePlanBootstrap.java      -> creates the sample plan, powers reset
  CorsConfig.java               -> lets the page (port 3000) call port 8080
  Subject.java  Task.java  StudySession.java   -> the data objects
  SubjectRepository.java  TaskRepository.java  StudySessionRepository.java

Lecture numbers refer to the lessons in public/java/studyplanner/lessons/ -
every idea in the backend has a direct relative among those demos.


--------------------------------------------------------------------------------
1. CLASSES AND OBJECTS  (Lectures 01-02, 10, 13)
--------------------------------------------------------------------------------
WHAT: A class is a blueprint; an object is a real thing built from it, with
      its own data.

WHERE: Subject.java, Task.java, StudySession.java

WHY: Subject is the form "course"; every course the student adds becomes one
     object: new Subject("CSC2104", "Java OOP", 240, "blue").


--------------------------------------------------------------------------------
2. CONSTRUCTORS  (Lecture 02)
--------------------------------------------------------------------------------
WHAT: A special method that runs when an object is created, to set it up.

WHERE: the main constructor of every domain class.

WHY: The constructor calls the setters, so a freshly built object is already
     complete and already checked ("constructors and object setup").


--------------------------------------------------------------------------------
3. ENCAPSULATION - private fields, getters, setters  (Lecture 18)
--------------------------------------------------------------------------------
WHAT: Hide the data (private); outside code can read or change it only
      through methods that check values first.

WHERE: every domain class, e.g. Task.setPriority(String):

    public void setPriority(String priority) {
        ...
        if (not Low, Medium or High) {
            throw new IllegalArgumentException("Priority must be...");
        }
        this.priority = ...;
    }

WHY: No page or user can sneak in an impossible value - bad data never gets
     saved. (Priority is a plain String here, checked with if, because
     enums have not been taught yet.)


--------------------------------------------------------------------------------
4. if / else AND LOOPS  (Lectures 05-06)
--------------------------------------------------------------------------------
WHAT: Conditions and for-each loops - the everyday control flow.

WHERE: PlannerController.allTasks() splits tasks into "open" and "done"
       lists; ProgressCalculator.compute() counts with plain counters.

WHY: No streams, no fancy syntax - literally "for each task: if completed,
     count it", Lecture 06 applied to real work.


--------------------------------------------------------------------------------
5. ArrayList AND HashMap  (Lecture 09 + practice sessions)
--------------------------------------------------------------------------------
WHAT: ArrayList holds many objects and grows; HashMap stores (key, value)
      pairs like a dictionary.

WHERE: PlannerController builds "open"/"done" ArrayLists;
       ProgressCalculator uses a HashMap<Long, Integer> to add up finished
       minutes per subject.

WHY: Plain collections are enough to sort the to-do list and draw the
     progress bars.


--------------------------------------------------------------------------------
6. THE static AND final KEYWORDS  (Lecture 19)
--------------------------------------------------------------------------------
WHAT: static belongs to the class itself, not to one object; final never
      changes after it is set.

WHERE: ProgressCalculator //

    public static final int DEFAULT_WEEKLY_GOAL_MINUTES = 600;
    private static int weeklyGoalMinutes = DEFAULT_WEEKLY_GOAL_MINUTES;

WHY: The weekly goal is one shared value for the whole app - static fits
     perfectly. (Subject, tasks and sessions survive restarts in the
     database; the goal keeps its value while the app is running.)


--------------------------------------------------------------------------------
7. INTERFACES  (Lectures 29-30)
--------------------------------------------------------------------------------
WHAT: An interface is a promise-list: method names a class agrees to provide.

WHERE: the small Completable interface at the top of Task.java (kept next to
       Task to save a file); StudySession makes the same promise:

    public interface Completable {
        boolean isCompleted();
    }
    public class Task implements Completable { ... }
    public class StudySession implements Completable { ... }

WHY: Tasks and sessions are different things, yet both can be finished -
     exactly the Lecture 30 Trackable idea.


--------------------------------------------------------------------------------
8. INHERITANCE AND toString() OVERRIDING  (Lectures 22, 27)
--------------------------------------------------------------------------------
WHAT: Every class inherits from Java's Object class; a child may replace
      (override) a method.

WHERE: every domain class overrides toString(); overriding an inherited
       method is the small, taught version of inheritance at work.

WHY: Printing any subject, task or session now describes it nicely.


--------------------------------------------------------------------------------
9. ANONYMOUS CLASSES FOR SORTING  (Lecture 21)
--------------------------------------------------------------------------------
WHAT: A class written exactly where it is used, with no name.

WHERE: PlannerController.allTasks() and allSessions():

    open.sort(new Comparator<Task>() {
        public int compare(Task a, Task b) { ... }
    });

WHY: Sorting needs "how to compare two items"; the anonymous Comparator is
     the one-off trick from Lecture 21 doing real work.


--------------------------------------------------------------------------------
10. EXCEPTIONS - BUILT-IN CLASSES + ONE CENTRAL CATCH  (Lectures 36-37)
--------------------------------------------------------------------------------
WHAT: When something is wrong, throw one of Java's own exception classes;
      catch it centrally and answer politely.

WHERE: setters throw new IllegalArgumentException("...");
       controller methods throw new NoSuchElementException("...") when an
       item is missing; ApiErrors.java catches both - plus bad JSON - in
       one @RestControllerAdvice class.

WHY: No new exception classes were invented. One catch-block turns problems
     into friendly JSON (400 wrong value, 404 missing item, 500 unexpected):
     the web version of Lecture 37 try/catch/finally.


--------------------------------------------------------------------------------
11. DATES - LocalDate AND LocalTime  (data types, Lecture 03 style)
--------------------------------------------------------------------------------
WHAT: Java types for a calendar date ("2026-10-21") and a clock time
      ("16:30") - strings with superpowers: they compare correctly and
      know .plusDays(1).

WHERE: Task.dueDate, StudySession.date/.time, ProgressCalculator's week math
       (Monday of the current week = today minus weekday - 1).

WHY: "Is the task overdue?" becomes simply dueDate.isBefore(today).


--------------------------------------------------------------------------------
12. HOW A TASK KNOWS ITS SUBJECT  (rows linked by id)
--------------------------------------------------------------------------------
WHAT: A task does not copy its subject's data; it stores one number, the
      subject's id.

WHERE: the Long subjectId field in Task.java and StudySession.java.

WHY: Matchable and simple: removing a subject removes every row whose
     subjectId equals that subject's id (PlannerController.removeSubject).


--------------------------------------------------------------------------------
13. SPRING BOOT - THE GLUE  (beyond the lectures, kept to a minimum)
--------------------------------------------------------------------------------
WHAT: A framework that gives your classes web addresses. Only a small fixed
      set of annotations is used:

      @SpringBootApplication      the start button
      @RestController             this class answers web requests
      @GetMapping/@PostMapping/@PatchMapping/@DeleteMapping + URL
      @PathVariable, @RequestBody receive an id / a JSON body
      @ResponseStatus(...)        which status code to answer with
      @Transactional              do this as one all-or-nothing step

WHERE: PlannerController.java holds all the URLs; the three repository
       interfaces declare method NAMES (findAll, save, findById,
       deleteBySubjectId...) and Spring writes their bodies; CORS is set
       once in CorsConfig so the page on :3000 may call :8080.

WHY: Every rule is still plain Java you could write in a lecture exercise;
     Spring only hands those rules to a web server.

Questions like "where is encapsulation really used?" - open any setter in
the domain classes and read the if-block; it is right there.

What the web app takes over instead of Java code:
- Console input (L32): the page gathers input and sends JSON over HTTP.
- File handling (L33-35): the H2 database in backend/data/ saves the rows.
- Threads (L40-48): the web server already runs requests in parallel; the
  lesson files still demo the threading concepts themselves.
